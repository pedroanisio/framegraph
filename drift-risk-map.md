### Coupling mechanism legend

- **codegen**: dependent is machine-derived from the source (stays in sync if the derivation runs).
- **shared-import**: dependent imports the source directly; the interpreter/type-checker enforces the contract.
- **manual-mirror**: dependent restates the source by hand; no automated enforcement.
- **contract-test**: a dedicated test asserts agreement between source and dependent.
- **build-step**: a build/render step produces the dependent from the source.
- **runtime-validation**: inconsistency is caught (or, when permissive, *not* caught) at parse/render time.
- **none**: no known enforcement mechanism.

### Propagation mode legend

`build-error` → `type-error` → `test-failure` → `lint-failure` → `runtime-error` → `silent` (loud → quiet). **silent** means the dependent is now wrong and nothing signals it.

### Finding C1: 15 of 17 sidecars are never validated against their patterns

**Source**: `framegraph/data/patterns/slides-patter-a.yml` — pattern zone definitions (roles + `content_type`).
**Dependent**: [`framegraph/data/fills/*.yml`](framegraph/data/fills/) — 17 sidecars (`pattern_id` + `zones` overrides + `example_fill`), e.g. ids `010 044 091 093 111 122 145 183 198 219 246 267 280 290 297 311 320`.
**Mechanism**: manual-mirror — each sidecar restates a pattern's roles in its `example_fill` and `zones`.
**Guard**: ⚠ effectively NONE.

- [`test_pattern_render.py`](tests/integration/test_pattern_render.py#L47-L58) validates **only** BMC (#44).
- [`test_cli_patterns.py`](tests/integration/test_cli_patterns.py) exercises **only** #44 end-to-end.
- The `wheel-smoke` CI job renders **only** #10 (SWOT).
- [`scripts/validate_fills.py`](scripts/validate_fills.py) — the tool *designed* to validate every sidecar — is **not** referenced by `Makefile`, `.github/workflows/ci.yml`, or `.pre-commit-config.yaml`.

**How drift manifests**: A maintainer renames a zone role in a pattern in
`slides-patter-a.yml` (say `risks` → `key_risks` on pattern #93, RAID Log). The
sidecar [`093-raid-log.yml`](framegraph/data/fills/093-raid-log.yml) still keys
its `example_fill` on `risks`. Nothing in CI re-validates that sidecar, so the
suite stays green. The break surfaces only when an agent or user runs
`framegraph patterns example 93` then `build` — a `pydantic.ValidationError`
(`extra inputs are not permitted` / `field required`) at point of use, in
production, not at PR time.

**Recommended fix**: Add a parametrized integration test that iterates
`framegraph/data/fills/*.yml`, loads each via `load_sidecar`, and validates its
`example_fill` against `derive_fill_schema_with_sidecar(pattern, sidecar)` for
the matching catalog pattern — failing per-id with the offending role. Then wire
`scripts/validate_fills.py` into `make check` and the `pytest`/`lint` CI jobs so
the contract is enforced on every PR. (Pairs with C2 — fixing the corpus path
gives most of this for free.)

**Source**: the runtime sidecar location `framegraph/data/fills/` (used by

`FILLS_DIR = …/static/refs/fills/`.
**Mechanism**: manual-mirror (a second hard-coded path that must agree with the runtime path).
**Guard**: ⚠ NONE — the test passes whether or not the path is correct.

`static/refs/fills/` **does not exist** in the tree. `_sidecar_for()`
([line 124-131](tests/integration/test_corpus_render_coverage.py#L124-L131))
short-circuits to `None` when `FILLS_DIR` is absent, so
`test_every_pattern_builds_to_svg` renders all 375 patterns with
*default* schemas only. Its docstring advertises it as
"the project's strongest guarantee that the fill-and-render pipeline works for
the whole catalog" — but the sidecar branch
(`derive_fill_schema_with_sidecar`, `item_kind: object` overrides) is **dead
code paths in the test**.

**How drift manifests**: identical to C1 — but worse, because the test's name
and docstring create *false confidence*. A reviewer sees a passing
"corpus render coverage" test and concludes sidecars are covered. They are not.
This is the most dangerous class of drift in the repo: a guard that reads as
present but silently does nothing.

**Recommended fix**: Point `FILLS_DIR` at `Path(framegraph.__file__).parent /
"data" / "fills"` (or import and reuse `cli._find_sidecar` / a shared resolver),
so the corpus test exercises every sidecar through the real schema-derivation
path. Add an assertion that the resolved sidecar directory exists and is
non-empty, so a future path move fails loud instead of silently degrading
coverage.

### Finding H4: `extra="allow"` on every object model swallows unknown/typo keys

**Source**: [`framegraph/_schema.py`](framegraph/_schema.py) — `model_config = ConfigDict(extra="allow")` on every object-type model (and on `Document`/`DeckDocument`).
**Dependent**: all authored YAML — `examples/*/*.yml`, `tests/fixtures/*.yml`, `static/fixture/*.yml`, and any user/agent-authored deck.
**Mechanism**: runtime-validation, intentionally permissive. **Guard**: partial — only fixtures wired into golden snapshots get an indirect visual check.

**Gap**: `{type: rect, colour: red}` (British spelling) or `{type: text, fill_color: ink}`
(wrong key) validates cleanly; the unknown key is dropped and the object renders
with defaults. Author intent and rendered output drift with **no** error at parse,
type-check, lint, or test time for un-goldened content. The schema's own header
comment ([`_schema.py:13-17`](framegraph/_schema.py#L13-L17)) acknowledges
`extra="allow"` is deliberate (plugin pass-through on `use`/`component`) — but it
is applied uniformly, including to closed core types.
**Upgrade path**: tighten core, non-extensible object models to
`extra="forbid"` (keep `extra="allow"` only where pass-through is required, i.e.
`use`/`component`/token blocks), or add an opt-in `framegraph validate --strict`
mode that reports unknown keys. The unknown-key set is large, so stage it: start
by forbidding extras on `rect`/`ellipse`/`text`/`line`/`connector` and expand.
Demotes to MODERATE.

## MODERATE Findings (summary)

- **#7 — `ContentType` Literal ↔ `_DEFAULT_TYPES` completeness.** `derive_default_fill_schema` uses the direct subscript `_DEFAULT_TYPES[ct]` ([`fill.py:207`](framegraph/patterns/fill.py#L207)); mypy does not enforce that a `dict[ContentType, …]` literal covers every Literal member. A new `ContentType` added without a `_DEFAULT_TYPES` entry raises `KeyError` at render time. *Fix*: `assert set(get_args(ContentType)) == set(_DEFAULT_TYPES)` as a unit test.
- **#8 — theme list additions slip the doc guard.** `test_documented_consulting_themes_present` asserts the documented 7-theme set is a *subset* of `list_themes()`; adding an 8th token pack passes while the docs (AGENTS/README/MANUAL) silently omit it. The test's own hard-coded set is itself a fourth mirror. *Fix*: assert set **equality** against `lib/tokens/*.yml`, and extract the documented set from the docs rather than hard-coding it.
- **#9 — DSL version is semantically inert + scaffold lags.** `Document.version` is validated as `float` only ([`_schema.py:825`](framegraph/_schema.py#L825)); no code maps a declared `version:` to a supported feature set, so `1.0`–`1.5` (and `99.0`) all pass. Meanwhile [`library.py:1242`](framegraph/library.py#L1242) scaffolds new decks with `version: "1.2"` while current authoring convention (AGENTS.md, fixtures) is `1.5`. *Fix*: centralize a `CURRENT_DSL_VERSION` constant used by the scaffold and (optionally) range-validated by the schema.
- **#10 — committed example SVGs drift from the renderer.** `make examples` regenerates `examples/*/*.svg`, but CI never runs it or diffs the result (only `wheel-smoke` renders to `/tmp` and discards). The 3 committed SVGs can silently lag the renderer. *Fix*: a CI step that runs `make examples` and fails on a non-empty `git diff`.
- **#11 — corpus test re-implements the content_type shapes.** `_default_value_for_content_type` ([`test_corpus_render_coverage.py:58`](tests/integration/test_corpus_render_coverage.py#L58)) hard-codes a minimal payload per content_type. It raises on an *unknown* type (a partial guard) and runtime-validates shapes, but a *relaxed* shape (field made optional) slips. *Fix*: drive the test payloads off `_DEFAULT_TYPES` rather than a parallel `if/elif` ladder.

### Heuristic limitations

This is static heuristic analysis (`grep`/`find`/file reads + targeted source
reading). It cannot detect couplings mediated by runtime reflection or
metaprogramming; it cannot prove the *completeness* of any test suite (a
"test-failure" propagation mode assumes the relevant test exists **and** runs —
Finding C2 is precisely a case where that assumption failed); and it judges
semantic equivalence structurally, so two definitions that look different but are
logically identical may be mis-scored. Per the skill's bias, uncertain couplings
were flagged rather than dropped. Validate all CRITICAL and HIGH findings against
the live code before acting.
